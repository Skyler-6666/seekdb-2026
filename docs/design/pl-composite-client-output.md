# PL 复合值的客户端输出设计

更新日期：2026-10-17。状态：Q23 及后续架构复核已确认；编码实现及普通/打包、文本/二进制协议接口验证已完成。当前公开 MySQL 语法无法构造 PL 复合返回值，验证使用实际运行时和协议接口，未声称完成此类 SQL 的网络端到端测试。见[验证记录](../implementation/table-functions-validation.md)。

## 职责与现状

SQL 内部的记录和集合保持为有类型的值。通用结果输出层负责在最终向 MySQL 客户端发送时编码这些值；同类型值无论来自 UNNEST、子查询还是其它表达式，都采用相同规则。表函数只交付列值，不承担 JSON 序列化，也不注册按函数选择的编码回调。

实现前，`fill_select_result_set` 在特定文本协议上下文将 PL 复合列元数据标记为 varchar，但并未完成值转换。普通和打包结果路径均缺少对应的 PL 复合值转换，公共编码器没有 ObExtendTC 分支；SQL ARRAY 已有的输出处理不能证明 PL 集合已可输出。基线源码依据见 [Q23 核查记录](./table-functions-decisions.md#q23pl-复合列的客户端表示已确认)。本次实现将转换放在共享结果输出层，并统一两种协议的元数据。

## 输出约定

尚无协议表示的 PL 复合值转换成单个 JSON 文本单元格：记录表示为对象，顺序集合表示为数组。带键集合的表示必须保留键；叶子值复用适用的已有 JSON 转换规则，无法表示时明确报错，不静默丢失成员。SQL 数组继续使用已有输出约定。

最新 master 的实现边界：当前启用的 PL 运行时没有带键关联数组的存储结构；MySQL SQL 入口也不能创建这些复合返回声明。实现保留内部记录及顺序集合的通用输出能力，并对非 NULL 关联数组明确返回不支持，不能将其按顺序数组编码而丢键。未来恢复带键运行时后需要补充保键编码；本次不声称已经实现这一缺失运行时的输出。

例如记录成员为 `id`、`profile`、`tags` 时，最终仍只有三列：

| id | profile | tags |
| --- | --- | --- |
| 1 | `{"city":"杭州"}` | `["数据库","AI"]` |

整个列值为 NULL 时发送 SQL NULL；非 NULL 复合值内部的空值表示为 JSON null，空顺序集合表示为 `[]`。DESCRIBE 展示逻辑列声明，MySQL 协议 metadata 如实描述实际传输的文本；列名、列序、列数保持一致，不要求两者使用相同的类型编码。

转换只发生在最终客户端输出时，SQL 内部继续对集合列执行 UNNEST、对记录列进行字段投影。编码与元数据生成使用一致的类型表示约定，普通与打包结果路径、文本与预处理语句二进制协议均遵守这一规则。

## 配套任务与验收

该任务与 PL 集合接入分别实现，在端到端交付时共同验收；从表函数框架中移出职责不意味着取消输出能力。

| 范围 | 验收要求 |
| --- | --- |
| 来源一致性 | 相同类型的 PL 值通过 UNNEST、子查询或其它可产生该值的表达式输出时，表示一致，不按函数名分支 |
| 协议路径 | 普通/打包输出、文本/二进制协议均可发送非 NULL 复合值，metadata 与实际编码一致 |
| 列契约 | 保留 SELECT 最终列名、列序和列数，不在编码时展开内部记录 |
| 值边界 | 记录、顺序集合、带键集合、嵌套值、空集合、整列 NULL 和内部 NULL；无法表示的叶子值明确报错 |
| SQL 内部语义 | 最终输出前的 UNNEST 和字段投影仍处理原有类型，不能提前变成 JSON 文本 |

总体接口、实施阶段与迁移验收见 [表函数与虚拟表设计](./table-functions.md)；决策见 [ADR 0004](../adr/0004-pl-composite-client-representation.md)。
