# 表函数与虚拟表重构设计访谈

状态：Q1–Q23 及后续六项架构复核修订均已确认。开始日期：2026-10-16；更新日期：2026-10-17。本文按最新决定同步各项约定，并在架构复核修订节记录变更原因；整理后的方案见 [完整设计](./table-functions.md)。当前仍是设计交付，不表示功能已经实现。

## 已明确的目标与约束

- 重新设计表函数的语法与实现框架，参考 DuckDB、PostgreSQL 的可取设计。
- 消除虚拟表自身占用的 schema 对象和相应持久化元数据。
- 不要求兼容旧接口；需要明确现有功能在新模型中的归属。
- 本轮先讨论设计，不实施代码、构建或部署。
- 用户倾向于用 `UNNEST(get_user_list(...))` 表达“先取得一个集合值，再展开为行”，保持两种职责清楚。

## 第一轮已确认的决策

- **Q1：消除范围。** 本轮只消除虚拟表自身的 schema 与相应元数据落盘；系统视图可以保留并改为查询表函数，其自身 schema 不属于本轮消除目标。
- **Q2：提供方式。** 本轮只建设内建表函数框架，不新增用户通过 SQL 创建表函数的能力；普通 PL 集合值函数通过 `UNNEST` 接入的设计方向保留。
- **Q3：名称空间。** 内建表函数采用全局名称，且用户明确要求不加冗余的 `seekdb_` 产品前缀；内存信息入口使用 `memory_info()` 作为当前命名示例。具体功能名仍需按含义确定，不能只机械删除旧虚拟表名称的前缀。

## 汇总方向

- 表函数使用 `FROM f(...)`；普通集合值函数通过 `UNNEST(...)` 接入，不因出现在 `FROM` 中而自动成为表函数。
- 移除通用 `TABLE(...)` 包装；保留 `JSON_TABLE` 的专属参数语法，接入共同的绑定结果约定。
- 表函数既可自行扫描并产生行，也可在绑定时展开成查询；绑定后分别成为统一函数扫描关系或普通派生表，复用现有查询体系。展开不执行数据查询。
- 每个虚拟表的能力均须有明确去向，初期可一一映射到独立命名的内建表函数，核对语义后允许合并。输出定义随程序发布，不创建持久化的表或存储函数对象。
- 采用明确的 `SHOW TABLE FUNCTIONS` 与 `DESCRIBE TABLE FUNCTION` 入口。固定输出可按函数名描述；依赖调用参数的输出需要区分按名称介绍规则和按调用确定列。
- 上述 SQL 为提议的新接口，不能据此认定现有 seekdb 已经支持。

## 第二轮已确认的决策

- **Q4：** `FROM f(...)` 只查找表函数，普通表达式中的 `f(...)` 只查找普通函数；允许两类同名，不做普通集合值函数到表函数的隐式转换。
- **Q5：** 名称形式描述固定列或动态输出规则；调用形式通过绑定确定具体输出，例如 `DESCRIBE TABLE FUNCTION unnest([1, 2])`。这些均为新语法提案。
- **Q6：** 内建函数声明权限要求，复用已有权限并保留真实对象的可见性过滤；本轮不增加逐函数 GRANT，不为每个内建函数预建持久化授权记录。

## Q7：记录元素的输出形式（已确认）

假设 `get_user_list()` 返回一个集合，元素的声明含有 `id`、`name` 两个成员。对于拟支持的 `SELECT * FROM UNNEST(get_user_list())`，有两种不同契约：一列完整记录，或者按声明顺序输出 `id`、`name` 两列。

UNNEST 的核心职责是把集合的元素转换为结果行；一列完整记录与直接用记录成员构成结果行，都可以承载这些元素。两种输出的差异是元素如何映射为结果行，不应将“集合变成行”和“记录成员成为列”混称为同一种展开。

已确认采用后者，即“记录元素直接构成结果行”的约定：一层成员对应列，名字取成员声明；成员中的集合或记录保持为该列的值，不递归增加行或字段。框架需要明确这一元素到行的映射规则，不能将其误解为递归拆解任意复杂值。此项是新设计决策，不表示现有 UNNEST 已经支持 PL 集合。

例如一个用户具有 `id`、`name`、`tags` 三个成员，其 `tags` 集合含两个元素：展开用户集合只生成一个用户行，`tags` 仍为一列集合值。对 tags 继续做集合展开属于另一个操作。

PostgreSQL 将数组 UNNEST 声明为 `anyarray → setof anyelement`，在 FROM 中对返回复合值的函数采用字段列映射；这两个约定分别见 [数组函数](https://www.postgresql.org/docs/18/functions-array.html)、[表函数](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-TABLEFUNCTIONS)。这说明按字段列呈现可以来自 FROM 对返回元素的处理，而不必把它解释为 UNNEST 的递归展开。

现状证据：seekdb 的 `TABLE(PL 集合)` 在 [resolver](../../src/sql/resolver/dml/ob_dml_resolver.cpp) 的 `resolve_function_table_column_item_udf` 中按记录成员输出列；本地 DuckDB 的 [UnnestBind](/home/nijia.nj/nijia.nj/duckdb-main/src/function/table/unnest.cpp:44) 将 LIST 的元素类型作为单列返回类型；本地 PostgreSQL 的 [composite 绑定](/home/nijia.nj/nijia.nj/postgresql-18rc1/src/backend/parser/parse_relation.c:1878) 使用记录的字段描述。不同实现具有不同的输出契约，统一框架本身不能替代这个决定。

## Q8–Q10 决策（已确认）

- **Q8：多集合输入。** 保留 `UNNEST(a, b, ...)`，按各集合的遍历顺序逐个配对，行数取最长输入的元素数，已耗尽的输入对应列补 NULL。例如 `UNNEST([1, 2], ['a']) AS t(n, s)` 输出 `(1, 'a')` 与 `(2, NULL)`。输入是否支持多集合与输出列默认命名分开决定。
- **Q9：单集合的空值语义。** 空集合和 NULL 集合产生零行；集合中的 NULL 元素仍占一行。这里的 NULL 集合指已能确定元素定义的集合值；裸 NULL 能否完成绑定是另一项问题，不能由零行规则推导。
- **Q10：别名与重名。** `AS t` 只改变关系的引用名；`AS t(a, b)` 按最终输出列的位置覆盖名称，允许只覆盖前若干列，超出列数报错。应用列别名后，同一个表函数调用内的输出列名应唯一；仍重名则报错并要求提供别名，不自动修改显式名称。此约束不改变外层 SELECT 可以产生重复结果标签，也不禁止不同查询来源各自具有同名列。

当前事实：seekdb 多数组 UNNEST 已采用短输入补 NULL，单独空/NULL 集合为零行，NULL 元素占一行；现有别名列表却要求与输入数完全相等，且允许重复列名。新设计不以兼容现状为约束。证据：[输入绑定](../../src/sql/resolver/dml/ob_dml_resolver.cpp)、[数组迭代](../../src/sql/engine/basic/ob_json_table_op.cpp)。PG 允许部分列别名并拒绝超额别名，见 [buildRelationAliases](/home/nijia.nj/nijia.nj/postgresql-18rc1/src/backend/parser/parse_relation.c:1218)；本地 DuckDB 的绑定对象拒绝重复列名，见 [Binding](/home/nijia.nj/nijia.nj/duckdb-main/src/planner/table_binding.cpp:18)。seekdb 行为由只读 SELECT 和源码核对，DuckDB/PG 本次只核对本地源码及已有测试。

## Q11–Q13 决策（已确认）

### Q11：默认列名

函数负责提供自己的有序默认列名，公共绑定流程应用列别名并检查唯一性。UNNEST 采用以下规则：

| 输入 | 默认列名 |
| --- | --- |
| 单个集合，元素是标量或内层集合 | `unnest` |
| 多个集合中的非记录元素 | `unnest_1`、`unnest_2` 等，数字取输入参数的位置，从 1 开始 |
| 元素是记录 | 使用成员声明的名字与顺序，例如 `id`、`name` |

多集合输出按输入顺序拼接各自的列。两个记录输入若都有 `id`，或记录成员名与生成名称相同，则按 Q10 要求调用处提供列别名；不为记录成员自动增加前缀或后缀。默认名称由函数约定决定，不根据输入表达式文本、来源列名或运行时元素值改变。

### Q12：关联调用

允许行值参数引用 JOIN 左侧已引入来源的列，不要求额外书写 LATERAL。例如 `FROM users AS u CROSS JOIN UNNEST(u.tags) AS t(tag)`，语义上针对每个用户展开其 tags，再将该用户与展开结果组合。需要保留没有 tag 的用户时使用 `LEFT JOIN UNNEST(u.tags) AS t(tag) ON TRUE`。

此规则仅适用于允许运行时传入的行值参数。用于决定输出列或展开查询结构的配置参数，能否逐行变化需要由其绑定契约明确，不能由关联语法推导为所有参数均可逐行变化。

### Q13：本轮输出列推导的边界

本轮仅由注册定义、集合元素声明和显式参数确定输出列：系统信息函数读取固定列定义，UNNEST 读取元素声明，JSON_TABLE 读取 COLUMNS 声明。描述 `UNNEST(get_user_list(...))` 的列时读取函数及元素的声明，不执行 get_user_list 来获取样本数据。

本轮不加入类似自动读取 JSON 数据再猜测字段的能力；若以后加入，应作为明确声明需要数据探测的绑定能力另行设计。该边界不意味着查询展开阶段不能读取目标表的元数据，也不表示所有绑定过程一律禁止 I/O。

## Q14–Q16 决策（已确认）

### Q14：参数何时求值

函数定义明确区分绑定时参数与执行时参数。决定输出列、目标关系或查询结构的输入必须在绑定时确定；决定每次调用数据值的输入则在执行时求值，允许符合 Q12 作用域的列引用。绑定时可以读取执行时参数的静态声明，但不为确定列而执行该表达式。

例如 UNNEST 在绑定时读取元素声明，执行时读取数组值；JSON_TABLE 的 COLUMNS 在绑定时形成列定义，JSON 文档表达式在执行时求值。现有 HYBRID_SEARCH 的表名与配置整体在绑定时消费，本轮迁入共同接口不自动承诺逐行改变搜索配置；将配置中的部分值改成执行时表达式属于后续能力。

架构复核进一步确定：GENERATOR 的 `n` 只影响行数，作为执行时整数参数，可接受占位符、普通表达式和合法的关联列引用；每次调用初始化时求值一次，重扫按输入重新求值并重置计数。新默认列名为 `generator`，正数产生 1 到 n，零/负数零行，NULL 报错。旧常量限定属于待消除的迁移限制。

参数依赖与缓存按 Q17 处理；绑定时参数允许的表达式形式和预处理参数限制按已确认的 Q20 处理。

### Q15：共同入口与两种实现路径

普通 `FROM f(...)` 经通用语法节点查找内建表函数注册项，不在通用 resolver 中逐个识别函数名；JSON_TABLE 的专属语法经适配后提供结构化选项，保留路径及 COLUMNS 的语义。

共同绑定入口接纳两种实现，并在绑定阶段完成分流：

- 扫描：交付扫描定义及输出列，形成统一函数扫描关系，执行阶段由对应实现产出行或批次；适用于 UNNEST、GENERATOR、JSON_TABLE 及系统信息函数。
- 查询展开：交付关系表达式或查询树，经普通查询绑定后成为派生表，不保留可执行的表函数包装；适用于 HYBRID_SEARCH。展开本身不运行查询，也不获取结果行。

两者在绑定结束时均接入现有关系表示。别名、列注册、权限、对象依赖和计划缓存复用现有查询机制，不新增贯穿优化与执行的双分支表函数关系管理。各实现保留自己的参数含义与数据来源；JSON_TABLE 的专属语义及 UNNEST 的记录映射留在各自实现中。

### Q16：投影与定位条件

首版框架把需要的列与迁移必需的定位条件传给扫描实现，由查询过滤提取并下推的条件全部保留在 SQL 层复核。以新的 `table_columns()` 为示意名称，查询某库某表的列信息时，可用库名和表名直接定位底层真实表，而不必先枚举所有对象。定位必须保证不漏行，不能用后续 SQL 复核弥补错误裁剪；复核所需的列纳入投影。

定位能力是函数声明的能力，不为其重新构建持久化虚拟表/索引对象。系统视图外层的筛选也需要有机会传递到相同接口；具体函数的必填定位参数与可选下推条件在迁移设计中分别明确。

通用谓词处理以及“完整满足条件后删除 SQL 过滤”的状态不在首版范围内，后续有明确收益和等价性证据时再增加。

## Q17–Q19 决策（已确认）

### Q17：缓存计划，不缓存本次扫描状态或系统数据

仅在依赖完整时缓存不可变的绑定结果和执行计划；运行时扫描状态、持有的资源与采集的数据不放入共享计划。系统信息函数在每次执行时读取数据，单次扫描内部的采样/快照语义由该函数定义，不能将一个查询的内存统计当作之后查询的结果。

真实表、索引、类型及存储函数版本复用已有对象依赖机制。首版在绑定时消费可变用户变量、依赖不完整或提供方尚不支持安全复用时，直接通过通用不可缓存标记阻止复用；不建设配置值追踪和失效通知体系。HYBRID_SEARCH 的绑定实现设置该标记，公共缓存逻辑不按函数名特判。普通执行时参数可以变化，但必须保持已绑定的输出契约；未知元素定义、会改变列结构的未确定参数不能被静默按旧结构复用。

### Q18：复用采集逻辑，适配新的执行上下文

复用现有 VT 的数据访问及采集逻辑，按需要修改适配层和基类依赖，不要求全部重写。公共扫描接口支持初始化、取批次、重扫和关闭；原有逐行扫描器可以经适配组成批次。执行状态归属本次执行，保存连接、迭代器、引用 guard、采样缓存等资源；结束、异常、取消和重扫都遵守明确的释放或重建规则。

适配不能为函数临时构造其自身的完整表/索引 schema，也不能继续通过原 VT ID 去 schema 管理器寻找自身定义。自身列信息来自函数描述符；对真实用户表和系统基表的 schema 访问仍保留。该选择不改变 PL 普通函数可能先生成完整集合的行为，也不保证全部旧 VT 都天然逐行实时采样。

### Q19：发现与描述返回普通单结果集

采用以下结果组织：

- `SHOW TABLE FUNCTIONS`：每个函数签名一行，返回 `function_name`、`signature`、`description`。
- `DESCRIBE TABLE FUNCTION name`：固定输出时每列一行，返回 `signature`、`column_position`、`column_name`、`column_type`、`description`；同名重载按签名分组。若该签名需要具体参数才能确定列，则返回一行规则说明，三个列信息字段为 NULL，不伪造输出列。
- `DESCRIBE TABLE FUNCTION call`：绑定具体调用，返回相同格式的列信息。调用可以附带与 FROM 相同的列别名，以便描述消除重名后的结果。

两个 DESCRIBE 形式都返回一个普通结果集，避免客户端必须处理多个结果集。函数目录仅展示随程序发布的定义与说明，不采集受保护的运行数据；真正调用时执行 Q6 的权限要求。具体执行错误或无法绑定的参数返回正常绑定错误，不以空列列表伪装成功。

## Q20–Q22 决策（已确认）

### Q20：绑定时参数和预处理参数的初期边界

绑定时参数接受字面量及可安全常量折叠的表达式，不执行 PL 用户函数或数据查询来取得这些值。直接执行的语句还可读取当前用户变量作为绑定时配置，以保留 HYBRID_SEARCH 的配置用法；首版只要绑定过程消费可变用户变量，就按 Q17 设置通用不可缓存标记。

预处理语句初期要求绑定时参数使用字面量或可安全折叠的常量；不支持用占位符或可变用户变量在 EXECUTE 时改变输出列、目标关系或展开结构。普通执行时参数仍支持占位符，但绑定时必须已能确定相应元素定义与输出契约；信息不足时返回明确错误，要求显式声明或固定结构。本轮不新增“执行时才重新发现输出列”的预处理机制。

### Q21：迁移完成标准

未来实现分阶段开发，交付时完成整体切换：先用 UNNEST 与 memory_info 验证公共绑定和扫描，再覆盖 JSON_TABLE、GENERATOR、HYBRID_SEARCH 及各类系统信息数据源，最后切换全部系统视图、SHOW 和内部查询消费者，并移除旧入口与 VT 自身 schema 生成/注册链路。

最终目标覆盖全部现有函数类 FROM 能力和本次构建启用的虚拟表；每个 VT 的能力有明确的目标函数及必要视图投影/筛选，初期可一一映射，语义核对后允许合并，不以函数个数等于旧 VT 个数验收。合并必须保留输出、权限和数据可见性约定；没有重复证据时不强行合并。VALUES 保持独立关系构造。沿用无需兼容的约束，以新实例验收，不增加旧实例的就地升级与历史 VT 元数据清理流程。该决定只规定未来实现计划，不授权当前修改、部署或清理现有实例。

### Q22：schema 与磁盘目标的验收口径

以下作为硬指标：新实例的 schema 管理器和系统表名字映射中没有 VT 自身的表/索引对象；bootstrap 不再写入这些对象的表、列、索引、历史版本与 DDL 元数据。真实系统基表、SQLite 数据、用户对象和保留的系统视图仍按自身规则持久化。

函数注册信息和输出列描述的必要内存单独计量；在相同构建配置与数据基线上比较启动后 schema 内存、元数据记录数及磁盘占用，报告实测结果，不预先承诺具体 MB 数。功能与性能验收同时覆盖过滤定位、权限、关联重扫、异常释放、SELECT/描述列信息一致性，以及重复执行获取当前数据。

## Q23：PL 复合列的客户端表示（已确认）

前提是已确认的 Q7：UNNEST 仅将记录的顶层成员变为列，内部记录和集合仍作为单个列值。因此即使列绑定成功，也需要确认客户端能够实际收到这些非 NULL 值。

最终输出路径的源码核查发现：

- [fill_select_result_set](../../src/sql/ob_sql.cpp) 按 SELECT 项逐个生成字段；局部变量 `composite_field_name` 没有赋值，并不构成递归拆列机制。PL 复合类型在特定文本协议上下文标记为 varchar，这一步只改元数据，不编码实际值。
- [普通结果输出](../../src/observer/mysql/ob_query_driver.cpp) 和 [打包结果输出](../../src/sql/engine/expr/ob_expr_output_pack.cpp) 对 SQL collection/geometry 有客户端转换，但缺少对应 PL 复合值转换。
- [公共单元格编码器](../../src/query/protocol/ob_mysql_protocol_util.cpp) 的 `build_cell_value` 处理 ObCollectionSQLTC，却没有 ObExtendTC 分支；未转换的 PL 复合值到此会报错。SQL ARRAY 已可发送不等于 PL 集合已可发送。

**已确认决策：** SQL 内部继续保留记录/集合值，在最终客户端输出边界为缺少协议表示的 PL 复合值提供 JSON 文本编码，每个值仍占一个单元格。记录使用对象、顺序集合使用数组；带键集合保留键，叶子值采用适用的已有 JSON 转换规则，无法表示时明确报错。整个列值为 NULL 时保留 SQL NULL。已有 SQL 数组的输出约定不因这一补充而改变。

DESCRIBE 返回逻辑列声明，协议 metadata 反映实际文本表示，两者的列名、列序、列数一致。实现验收覆盖普通/打包结果路径和文本/二进制协议，并验证空集合、NULL、嵌套值以及非 NULL 记录。SQL 内部继续对集合列使用 UNNEST 或投影记录字段，不受最终文本编码影响。本轮仅确认设计，尚未实施输出转换。

架构复核明确此能力归属通用结果输出层，作为独立配套任务实现；同类型值无论来自 UNNEST、子查询还是其它表达式，都使用相同编码。表函数只交付有类型的列值，不注册序列化回调。配套规格见 [PL 复合值客户端输出设计](./pl-composite-client-output.md)。

## 架构复核修订（2026-10-17，已确认）

用户要求检查特殊处理、架构职责和过度设计，并接受以下六项调整；上文相关决策及主设计已同步修订。

| 项目 | 已确认的修订与原因 |
| --- | --- |
| 绑定结果 | 扫描形成统一扫描关系，查询展开绑定为普通派生表；结束时回到现有关系体系，避免新建贯穿优化与执行的双分支关系管理 |
| PL 客户端编码 | 保留 Q23 行为，由通用结果输出层独立实现；表函数接口不承担递归 JSON 编码，所有输出来源共享类型转换规则 |
| 缓存 | 复用已有对象依赖，绑定时消费可变用户变量直接不缓存；通用标记取代函数名特判，首版不建设配置值追踪体系 |
| 过滤下推 | 首版只实现投影及迁移必需的定位，下推过滤仍由 SQL 复核；移除 SQL 过滤及通用谓词处理后置 |
| GENERATOR | 取代此前沿用 COLUMN_VALUE 与常量参数的约定；默认列名 generator，n 为执行时整数参数，因为它不决定输出列 |
| VT 映射 | 将原先每个 VT 一个函数的要求改为逐项能力覆盖；初期允许一一映射，语义核对后可以合并，避免固化历史划分 |

继续保留 JSON_TABLE 专属语法、UNNEST 自身的记录元素映射、两种 DESCRIBE 形式，以及执行状态、权限和资源释放要求。此轮仅修订文档，未进入代码实现。

## 已核查的现状与设计影响

- `INFORMATION_SCHEMA.PROCESSLIST` 与 `V$OB_MEMORY` 自身是 `SYSTEM_VIEW`，定义引用具体 VT 名称。迁走被引用的 VT 并不会自动消除视图自己的对象定义。证据：[视图定义](../../src/share/inner_table/ob_inner_table_schema_def.py)。
- SHOW 重写依赖 VT 名称，运行时工厂依赖 VT 的 ID 和 schema version；完成迁移必须调整这些内部消费者。证据：[SHOW resolver](../../src/sql/resolver/cmd/ob_show_resolver.cpp)、[迭代器工厂](../../src/observer/virtual_table/ob_virtual_table_iterator_factory.cpp)。
- 扫描器对被展示的真实库表执行可见性检查；取消函数自身的对象身份，不代表能删除这种结果过滤。证据：[虚拟表权限检查](../../src/observer/virtual_table/ob_virtual_table_iterator.cpp)、[分区信息过滤](../../src/observer/virtual_table/ob_information_partitions_table.cpp)。
- 现有 routine 授权写权限表、历史记录和 schema operation。设计推论：若新函数允许可配置且重启后保留的逐函数授权，需要保存授权状态；这与持久化函数定义是两回事。Q6 已决定本轮不新增逐函数授权。证据：[grant_routine](../../src/share/schema/ob_priv_sql_service.cpp)。
- 当前函数类 FROM 入口为 TABLE（PL 集合/GENERATOR）、UNNEST、JSON_TABLE、HYBRID_SEARCH。VALUES 是独立的关系构造语法，未遗漏为表函数。证据：[resolver 分派](../../src/sql/resolver/dml/ob_dml_resolver.cpp)、[TABLE 输入检查](../../src/sql/resolver/ob_resolver_utils.cpp)。
- HYBRID_SEARCH 的表名仅接受 literal，配置接受 literal 或用户变量，resolver 当场读取配置并生成子查询；展开前读取目标表、列、分区及索引信息。当前还明确禁止 HYBRID_SEARCH 计划加入缓存，因此新接口不能仅凭函数名就声称可以复用其绑定结果。证据：[语法](../../src/sql/parser/sql_parser_mysql_mode.y)、[展开](../../src/sql/resolver/dml/ob_dml_resolver.cpp)、[schema 读取](../../src/sql/hybrid_search/ob_hybrid_search_executor.cpp)、[缓存判断](../../src/sql/ob_sql.cpp)。
- 内存统计扫描按所需列输出，并在一次扫描中收集统计到私有 scanner；它不代表所有 VT 都是逐行实时采样。列元数据查询可从 key ranges 提取库表等值条件直接定位，SHOW TABLES 更要求提供数据库 ID。现有 VT 索引相关入口承载的是访问能力，不能将其统称为完整范围扫描索引。证据：[内存统计](../../src/observer/virtual_table/ob_all_virtual_memory_info.cpp)、[列元数据定位](../../src/observer/virtual_table/ob_information_columns_table.cpp)、[SHOW TABLES](../../src/observer/virtual_table/ob_show_tables.cpp)、[VT 索引优化](../../src/sql/optimizer/ob_join_order.cpp)。
- VT 数据源还包括 SQLite 生成扫描器和经 SQL proxy 读取真实系统表的扫描器。SQLite 扫描需要连接、prepare/step/finalize 生命周期，计划对象扫描需要引用 guard；公共状态不能只保存行游标。本轮只读核查未找到必须从只读行源框架排除的确切反例，但这不能替代后续逐函数迁移核对。证据：[SQLite 生成扫描器](../../src/share/inner_table/generate_inner_table_schema.py)、[系统表扫描](../../src/observer/virtual_table/ob_virtual_core_inner_table.cpp)、[计划对象访问](../../src/observer/virtual_table/ob_all_virtual_sql_plan.cpp)。
- VT schema 的消除需要覆盖生成器的 VT/table-index creators、启动构造与系统表名字映射、bootstrap 元数据写入输入，以及旧工厂的自身 schema 查找。SQLite 基表生成与系统视图 creators 必须保留；注册内存中没有 VT 对象与系统表中没有 VT 元数据需要分别验收。证据：[生成器](../../src/share/inner_table/generate_inner_table_schema.py)、[schema 构造](../../src/share/schema/ob_schema_utils.cpp)、[名字映射](../../src/share/schema/ob_schema_struct.cpp)、[bootstrap](../../src/rootserver/ob_bootstrap.cpp)、[元数据生成](../../src/share/inner_table/ob_dump_inner_table_schema.cpp)、[元数据写入](../../src/rootserver/ob_load_inner_table_schema_executor.cpp)。
